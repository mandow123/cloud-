## 阅读说明：先把几件容易误解的事说清楚

### 1. KAI Cloud 不是 GPU 所有者

KAI Cloud 通常不拥有供应商的 GPU、服务器、NAS 或机柜。平台做的是把不同供应商的服务整理成可以比较、下单、交付和验收的产品。

客户买到的是一份明确的服务使用权，例如：

> 在 2026 年 9 月 1 日 20:00 至 9 月 2 日 08:00，使用 4 张 H100 80GB GPU，出现故障时由供应商在约定时间内替换。

客户不是在平台上购买股票、代币、储值余额或设备所有权。

### 2. “容量”不是钱

本文所说的容量，是某种资源在某个时间段内能够提供的数量。例如：

- 100 张 GPU × 10 小时 = 1,000 GPU 小时；
- 100 万 Token/小时 × 5 小时 = 500 万 Token 的预留吞吐小时；
- 20 TiB 存储 × 100 小时 = 2,000 TiB·小时。

这些只是资源数量的记录，不是可以自由转账或兑换现金的钱包余额。

### 3. 不同资源不能直接互换

GPU 小时不能物理变成 NAS 小时，NAS 也不能变成 Token。平台只能在某个时间点使用统一参考价格，把不同资源换算成一个比较尺度，用于报价、组合采购或双方置换补差。最终交付的仍然是具体的 GPU、模型、存储或机柜服务。

### 4. 首阶段只验证一条最小交易链路

第一阶段不追求同时接入所有资源，而是先跑通：

> 一个地区 + 一个 GPU 产品 + 一家企业供应商 + 一家企业采购方 + 一笔真实订单。

只有付款、交付、验收、退款和对账都能正确完成，平台才逐步扩大资源类型和供应商数量。

## 第一章　商业逻辑：为什么需要这个平台

### 1.1 市场缺的不是“算力概念”，而是可执行的订单

供应商可能说“我有很多 GPU”，采购方可能说“我需要一批算力”。但一笔订单要真正执行，还必须回答：

1. 具体是什么型号和规格？
2. 在什么地区、什么时间可以使用？
3. 真实可交付数量是多少？
4. 价格是否包含电费、网络、存储、税费和最低消费？
5. 付款后谁负责开通、计量和验收？
6. 交付失败时谁退款、替换或赔偿？

KAI Cloud 的核心工作，就是把“我有算力”变成一份能够执行的服务约定。

### 1.2 平台为三方提供什么价值

| 参与方 | 原来的问题 | 平台提供的帮助 |
|---|---|---|
| 采购方 | 到处询价，难以比较，付款后还要追交付 | 统一规格、可比较报价、订单、验收和对账 |
| 供应商 | 有闲置容量但找不到客户，库存容易重复承诺 | 企业获客、资源验真、容量上架和结算 |
| KAI Cloud | 不想先投资建设全部底层设备 | 用标准、验真、订单和交付系统收取服务费 |

### 1.3 完整交易闭环

```text
供应商提交资源
    ↓
平台核验供应商和资源
    ↓
明确规格、时间、数量、价格和交付方式
    ↓
上架或回应采购询价
    ↓
订单锁定容量
    ↓
付款、开通、使用、计量
    ↓
采购方验收
    ↓
供应商结算、平台收取服务费、代理获得约定佣金
    ↓
沉淀可核验的报价、交付和成交数据
```

### 1.4 平台真正积累的资产

平台不应只追求注册量和挂牌金额，真正有价值的是：

- 经过核验的供应商和资源；
- 可比较、可解释的价格；
- 可以重复执行的交付流程；
- 可以复核的订单、计量、验收和结算记录。

### 1.5 冷启动原则

平台先围绕真实采购需求寻找少量匹配供应商，用人工验真和项目经理保障前几笔交易。重复出现的人工步骤，再逐步做成系统功能。

## 第二章　商业模式：钱从哪里来、流向哪里

### 2.1 主要收入来源

| 收入来源 | 谁可能付费 | 什么时候收取 | 客户买到什么 |
|---|---|---|---|
| 成交服务费 | 供应商，或由合同约定双方分担 | 订单验收并进入结算后 | 获客、订单、容量锁定、交付和对账 |
| 企业采购服务费 | 采购方 | 按项目节点或合同约定 | 需求梳理、筛选供应商、比价和项目协调 |
| 供应商系统与验真服务 | 供应商 | 按次、按容量或按年 | 资源核验、连接器、库存和报价工作台 |
| 计量和服务等级管理 | 买卖双方按合同分担 | 随订单或按月 | 用量记录、故障证据、服务达标判断 |
| 行情与数据服务 | 企业、供应商或研究机构 | 数据达到可发布标准后 | 历史价格、采购基准、API 和交付质量数据 |

平台不以客户充值后沉淀的资金、容量升值承诺、虚构成交或多层级拉人分成作为收入来源。

### 2.2 一笔 100 元订单的钱怎么分

下面只是说明分账逻辑的示例，不是固定费率。

假设一笔订单客户实际支付 100 元，合同约定：

- 供应商服务收入：94 元；
- KAI Cloud 服务费总额：6 元；
- 从该服务费内分配的直接代理佣金：3 元；
- KAI Cloud 净收入：3 元。

钱的流转可以理解为：

```text
客户支付 100 元
    ↓
持牌支付机构确认收款
    ↓
供应商完成开通和交付，客户使用并验收
    ↓
按合同结算：供应商 94 元 + KAI Cloud 净收入 3 元 + 服务费内直接代理佣金 3 元
```

平台服务费记为 F、费内佣金记为 C，必须满足 `0 ≤ C ≤ F`。供应商始终只扣一次平台服务费，佣金不重复扣减；买家也不因推荐关系被另行加价。实际项目还可能涉及税费、支付通道费、发票和退款，最终以合同和支付产品规则为准。**如果没有代理，这笔订单不会自动增加一笔代理佣金。**

### 2.3 平台看重交易质量，而不是流水大小

```text
平台净收入
= 已确认服务收入
- 支付通道成本
- 代理佣金
- 验真、交付和客服成本
- 退款、赔付和冲正
```

平台必须证明：供应商能卖出真实可交付容量，采购方能更快拿到合适资源，平台能控制退款、欺诈和人工交付成本。

## 第三章　客户到底买到什么

### 3.1 客户买的是“标准服务包”

一份标准服务包至少写清楚：

```text
资源类型和规格
数量和可使用时间
地区和网络边界
性能承诺
价格和包含的费用
开通方式
怎么计量
怎么验收
故障怎么替换或退款
```

客户最终获得的是主机、容器、API、存储入口或机柜服务及其使用凭据，不是一个抽象的“算力数字”。

### 3.2 五类首发资源

| 资源 | 计价例子 | 客户实际得到什么 |
|---|---|---|
| GPU | 单卡小时、服务器小时 | 云主机、容器、裸机账号或指定 GPU 使用时段 |
| Token 服务 | 百万 Token，或每小时承诺吞吐 | 有额度和计量规则的模型 API |
| 模型服务 | 模型实例小时、预留吞吐小时 | 指定模型版本、并发和性能档位 |
| NAS 存储 | TiB·小时、TiB·月 | 存储入口、容量、协议、性能和数据删除规则 |
| 机柜与功率 | 机柜月、kW·月 | 机位、功率、网络、冷却和进场服务 |

### 3.3 Token 预留和 Token 实际用量不是一回事

- **Token 实际用量**：客户真实调用了多少 Token，按实际使用计费；
- **Token 预留吞吐**：客户购买某个时间段内保证的处理能力，适合需要稳定并发的业务。

同一个模型可以同时存在两种价格，但不能把它们混成一个单价。每笔 Token 订单还必须写明模型、服务商、上下文档位、输入/缓存/输出计量、地区和有效期。

### 3.4 长短期资源不能随意混成一个单位

机柜通常按月采购，GPU 可能按小时采购。平台可以用 720 小时作为比较月份的参考，但真正结算仍以合同约定的实际周期为准。

## 第四章　资源如何从供应商到客户

### 4.1 一个 GPU 供应商的例子

假设某供应商在上海有 8 张 H100 80GB，未来 7 天每天可用，但每天保留 6 小时维护时间，已有 200 GPU 小时被其他订单占用。

```text
理论容量 = 8 张 × 24 小时 × 7 天 = 1,344 GPU 小时
可售容量 = 1,344 - 维护保留 - 已占用容量
```

供应商不能只填“我有 8 张卡”，还必须说明每个可售时间段。平台核验后，生成明确的可售批次，例如：

> 上海 / H100 80GB / 600 GPU 小时 / 指定时间窗 / 单卡小时价格 / 开通方式和验收规则。

客户下单 100 GPU 小时后，平台把这 100 GPU 小时从“可售”改成“已锁定”，剩余容量才能继续销售。

### 4.2 交付步骤

1. 供应商提交企业和资源资料；
2. 平台核验资源规格、归属和可用时间；
3. 供应商确认价格、起订量、服务承诺和交付方式；
4. 平台把资源发布为可购买或可询价服务；
5. 客户下单，平台锁定容量；
6. 供应商开通主机、容器、API 或存储入口；
7. 客户开始使用；
8. 供应商和平台分别记录用量、性能和故障；
9. 客户验收；
10. 平台按合同结算，并释放未使用容量。

## 第五章　平台定位与边界

### 5.1 “算力交易所”只是业务名称

本文所称“算力交易所”，实际指企业算力服务交易平台，不是依法设立的证券交易所、期货交易所，也不发行货币、证券或承诺收益的资产。

### 5.2 平台负责什么

- 统一产品规格和计价单位；
- 核验供应商主体和资源真实性；
- 维护可售容量，防止同一资源重复销售；
- 支持固定价、询价、预留和受控置换；
- 连接支付、交付、计量、验收、退款和结算；
- 保存订单、证据、发票和对账记录；
- 支持单层代理归因和结算后佣金。

### 5.3 平台不负责什么

- 不承诺算力容量升值；
- 不提供充值、自由转账或提现钱包；
- 不提供杠杆、保证金、期货、永续合约或自动做市；
- 不用报价数据冒充真实成交；
- 不允许未验真的资源直接成为可立即购买库存；
- 不允许供应商通过取出容量逃避已经成交的订单；
- 首阶段不开放个人资源自由转售和多层级返佣。

## 第六章　平台怎样描述一项资源

为了避免“大家都说自己有算力”但无法比较，平台把一项服务拆成三层：

1. **产品定义**：买的是什么，例如“H100 80GB 单卡小时”；
2. **可交付批次**：哪家供应商、在哪个地区、什么时间能交付多少；
3. **销售条件**：价格、最小购买量、有效期、服务承诺和购买方式。

这三层分别回答：

> 买什么？谁能在什么时候交付多少？按什么条件购买？

订单创建时，平台固定当时的产品规则版本。之后规则更新，也不能偷偷改变已经成交的订单。

## 第七章　容量记录：不是钱包，而是库存账

### 7.1 什么叫“存入”和“取出”

- **存入容量**：供应商把已经核验、承诺可以交付的未来服务写入平台库存；
- **取出容量**：供应商释放尚未被报价、订单或交付义务占用的剩余库存；
- **容量账本**：记录库存从可售到锁定、交付、消耗、释放的变化，不记录客户资金余额。

可售容量的基本公式是：

```text
可售容量
= 已核验并存入的容量
- 报价预留
- 已锁定订单
- 正在交付的容量
- 已消耗容量
- 风险冻结容量
```

### 7.2 为什么每次变化都要留下记录

平台不能直接把“剩余 100 小时”改成“剩余 50 小时”。每次存入、预留、锁定、消耗、释放或退款，都要新增一条记录，说明：

- 变了多少；
- 变更前后是多少；
- 因为什么订单或事件变化；
- 谁在什么时间操作。

这样才能回答“这 50 GPU 小时去哪了”，也才能避免超卖和账目不一致。

### 7.3 供应商申请取出时检查什么

平台会检查：

- 申请人是否有权操作这批容量；
- 申请数量是否没有超过剩余可售量；
- 是否已经被报价、订单、交付、退款或争议占用；
- GPU 或模型任务是否结束，NAS 数据是否完成迁移和删除；
- 是否满足合同规定的提前通知期；
- 是否存在风险冻结或司法冻结。

取出可以是立即取出、部分取出或排期取出。历史订单和历史记录不会被删除。

## 第八章　供应商准入与资源验真

### 8.1 首阶段为什么优先企业供应商

因为平台需要核对企业主体、授权经办人、对公账户、开票资料和资源归属。供应商状态可以简单理解为：

```text
待提交 → 审核中 → 已认证 → 受限 → 已暂停 → 已退出
```

“已认证”只代表在规定时间和范围内通过核验，不代表供应商永远不会出问题，所以还需要定期复核。

### 8.2 三种接入方式

| 方式 | 适用场景 | 平台能确认什么 |
|---|---|---|
| 人工资料 + 远程测试 | 首笔交易、小供应商 | 运营人员核对资料并运行测试；库存不能宣传成实时库存 |
| 轻量连接器 | 自有 GPU、服务器、NAS | 规格、可用状态、任务和定期心跳 |
| 云厂商只读 API 或子账号 | 云资源和模型配额 | 规格、配额、账单和运行状态；不接收主账号密码 |

连接器不应要求供应商上传 SSH 私钥、云主账号密码或 root 密码。它只采集验真、库存、计量和服务达标所需的数据。

### 8.3 GPU 至少要核验什么

1. 资源归属或托管关系；
2. 型号、显存、驱动和连接拓扑；
3. 标准测试任务和显存错误；
4. 网络、存储和温度等交付条件；
5. 持续在线状态；
6. 是否已经在别的平台重复承诺。

关键规格变化、心跳中断或核验过期时，资源应暂停接受新订单，进入重新核验。

### 8.4 公开信息和保密信息分开

公开页面可以展示供应商等级、脱敏地区、产品规格、可用时间、服务承诺和标准化价格。

设备唯一标识、机房详细地址、资源证明、供应商底价、风控备注和原始报价不应公开给无关人员或竞争供应商。

## 第九章　行情与价格：怎样比较不同报价

### 9.1 三种价格不要混在一起

1. **市场参考价**：同类产品、地区和计价口径下，多个有效报价和成交的统计结果；
2. **供应商报价**：某一家供应商愿意接受的价格和有效期；
3. **订单执行价**：买卖双方在某一笔订单中最终确认的价格。

市场参考价不是强制成交价，供应商报价也不等于真实成交价。

### 9.2 什么叫“标准化价格”

不同供应商的报价经常包含不同内容。有人含网络和电费，有人只报裸 GPU，所以平台要把条件放到同一个比较口径：

```text
标准化总成本
= 资源价格
+ 税费调整
+ 电费
+ 网络和流量
+ 必选存储
+ 开通费和最低消费的摊销
+ 可以解释的服务风险调整

标准化单价
= 标准化总成本 ÷ 可交付的标准单位
```

这只是比较工具，不代表平台修改了供应商原价。每个调整项都要能追溯到原始报价和计算依据。

### 9.3 P25、P50、P75 到底是什么

这里的 P 是“分位数”，用来描述一批可比报价的分布。它不是手续费，也不是三种固定售价。

假设有 100 个满足相同产品、地区、时间和计价口径的有效报价：

- **P25**：约 25% 的报价不高于这个价格；
- **P50**：中位数，约一半报价不高于它，另一半不低于它；
- **P75**：约 75% 的报价不高于这个价格。

通常可以这样读：

| 指标 | 采购方的直观理解 |
|---|---|
| P25 | 偏低价格，可能伴随更高起订量、更窄时间窗或更严格条件 |
| P50 | 一般市场价格 |
| P75 | 偏高价格，可能伴随更灵活交付或更完整服务 |

如果你看到的是 P20，它的意思只是“约 20% 的有效报价不高于这个价格”。本版统一使用 P25、P50、P75。

行情页面必须同时展示样本量、地区范围、计价口径、更新时间和有效期。样本不足时，不发布分位数结论。

### 9.4 指数和 K 线不是订单价格

- **价格指数**：固定一篮子产品的总体成本变化；
- **K 线**：按时间展示真实成交价的变化；
- **报价曲线**：展示供应商当前愿意怎么报价。

三者必须分开标记。没有真实成交的日期显示“无成交”，不能用报价或人工填充制造 K 线。

## 第十章　交易方式

### 10.1 固定价购买

适合规格清楚、库存新鲜、交付流程标准的资源。采购方确认数量和时间，平台先锁定容量，再生成待支付订单。

### 10.2 询价

询价适合大批量 GPU、机柜月、复杂 NAS 或定制模型服务。采购方描述需求，供应商提交报价，平台把不同报价转换成可比较的格式。供应商之间不应互相看到对方的原始底价。

### 10.3 预留容量

采购方提前锁定未来某个时间段的服务。预留费、取消规则、数量变化和交付前复核必须写进合同。

### 10.4 双边置换

双边置换是“我提供一种服务，你提供另一种服务”的受控交换，不是把容量变成货币。

置换前必须做到：

1. 双方资源都经过核验并写入各自库存；
2. 平台分别计算两边的真实服务数量；
3. 使用同一时间点的参考价格计算比较金额；
4. 展示原始单位、数量、价格来源、参考价值和补差金额；
5. 双方确认后分别锁定资源；
6. 任一边交付失败时，按合同整体回滚或进入争议处理。

客户最后得到的仍是具体的 GPU、Token、NAS、模型或机柜服务。

### 10.5 首阶段不开放

首阶段不开放匿名竞价、自动做市、杠杆、保证金、自由转让、个人现金回购、跨币种套利和没有真实交付基础的价格合约。

## 第十一章　订单、支付、交付、计量和结算

### 11.1 一笔订单的完整顺序

```text
确认需求或询价
→ 检查并预留容量
→ 创建待支付订单
→ 支付机构确认收款
→ 正式锁定容量
→ 供应商开通服务
→ 客户使用
→ 双方记录用量和故障
→ 客户验收
→ 退款、结算和佣金处理
```

### 11.2 为什么前端“支付成功”不能作为最终依据

浏览器页面可能因为网络中断、重复点击或伪造请求而显示错误状态。平台只能接受银行或持牌支付机构的服务端签名通知，并核对：

- 订单号和支付流水号；
- 商户、金额和币种；
- 通知签名；
- 是否已经处理过；
- 是否存在退款或撤销。

### 11.3 计量和验收怎么做

“计量”是记录客户实际用了多少；“验收”是客户确认供应商已经按约定交付。

平台可以同时读取供应商记录和平台侧记录进行比对：

- GPU：卡数、使用时长、作业是否可运行；
- Token：模型、输入/缓存/输出 Token、错误率和延迟；
- 模型实例：在线时长、并发、吞吐和版本；
- NAS：可用容量、性能、迁移和删除确认；
- 机柜：机位、功率、网络、开通时间和服务可用性。

两边记录差异超过合同阈值时，暂停自动结算，先人工复核。

### 11.4 退款、失败和争议

每一种异常都必须明确三件事：

1. 未使用的容量是否释放；
2. 钱如何退款或赔付；
3. 平台服务费和代理佣金是否冲回。

---

## 第十二章　代理合作与佣金

### 12.1 代理是谁

代理是经过平台审核、能够推荐真实企业需求的单层合作伙伴。代理可以是渠道伙伴、产业服务商或项目协作方。

代理不是靠发展下级代理赚钱的人，也不是只注册账号或转发链接就自动获得佣金的人。

### 12.2 为什么要给代理佣金

企业算力采购通常需要找到真实需求、确认规格、协调预算和推动交付。代理如果带来有效企业订单，就为平台减少了获客和商务协调成本。

因此佣金是对“有效获客和成交协作”的报酬，不是平台强制向客户额外收取的费用。

### 12.3 佣金什么时候产生

必须同时满足：

- 代理主体、协议、收款和税务资料审核通过；
- 在订单创建前完成客户归因；
- 被推荐企业在有效归因期内创建订单；
- 订单完成交付并通过验收；
- 订单进入结算。

支付成功不等于佣金已经可以结算。退款、拒付、赔付或欺诈订单会冲回佣金。没有代理的订单，不产生代理佣金。

### 12.4 明确不做什么

- 不收取代理入门费；
- 不按发展人数计酬；
- 不从下级代理的订单中继续分成；
- 不允许已结算佣金被直接改写，只能通过反向记录更正。

## 第十三章　技术架构：给产品和研发团队的说明

技术架构可以分成五层：

1. **身份和权限层**：区分采购方、供应商、代理和平台运营人员；
2. **产品和市场层**：管理产品规格、报价、行情、询价和订单；
3. **资源和交付层**：管理资源核验、容量、开通、计量和验收；
4. **支付和结算层**：管理支付回调、退款、供应商应付、服务费和佣金；
5. **风险和审计层**：管理争议、冻结、异常和操作记录。

技术上应保证：

- 同一订单重复通知只入账一次；
- 容量锁定和订单状态同步完成，不能出现“钱收了但容量没锁住”；
- 余额变化采用追加记录，不直接覆盖历史；
- 原始证据和公开页面分开保存；
- 所有人为操作都记录操作人、理由、前后状态和时间。

技术对象名称如 `CapacityProduct`、`CapacityLot`、`Listing` 只是系统内部名称，分别对应“产品定义、可交付批次、销售条件”，不代表三种可交易货币。

## 第十四章　安全、隐私和可信治理

### 14.1 连接器默认不可信

连接器每次上报都应验证设备身份、短期凭证、签名、时间和权限。连接器失联时，不必马上删除历史资源，但应暂停新订单并触发重新核验。

### 14.2 不收集高风险主账号凭据

平台不应在浏览器、聊天或普通表单中收集云主账号密码、SSH 私钥或 root 密码。优先使用只读权限、子账号、一次性配对码、短期凭证和安全交付链接。

### 14.3 数据最小化

平台只处理主体核验、资源验真、交易、交付、计量、结算和法定义务所需的数据。客户模型、训练数据和 NAS 文件内容不应被无关人员读取。

### 14.4 市场规则公开

平台应公开供应商准入、资源验真、报价、成交、退款、争议、代理归因和违规处置规则，并保留历史版本，避免事后改变规则影响已经成交的订单。

---

## 第十五章　合规边界

本白皮书不替代律师、税务顾问、审计机构、支付机构或主管部门的专项意见。正式运营前至少要确认：

- 平台运营主体和销售主体；
- 合同、发票和税务责任；
- 支付机构和资金分账方案；
- 是否触及电信、云服务或数据中心相关许可；
- 个人信息、客户数据和跨境数据处理边界；
- 电子合同、订单、验收和交易记录的保存方式。

首阶段原则上以中国境内、人民币、企业间交易为边界。跨境资源、外币支付、香港主体和跨境数据不得与境内订单静默混用，必须另行评估。

---

## 第十六章　平台指标：怎样判断做得好不好

平台不以注册量和挂牌金额作为唯一成功标准，而看以下指标：

| 维度 | 需要观察什么 |
|---|---|
| 资源质量 | 资源核验通过率、心跳新鲜度、重复资源拦截率、实际可交付率 |
| 市场质量 | 有效报价数量、报价更新时间、询价响应率、成交覆盖率 |
| 交易质量 | 容量预留成功率、支付成功率、重复回调处理正确率、超卖次数 |
| 交付质量 | 开通时间、首次开通成功率、计量一致率、服务达标率 |
| 财务质量 | 对账差异、退款时长、供应商结算准时率、佣金冲正准确率 |
| 客户价值 | 复购率、采购节省、供应商容量利用率、争议率 |

必须保持为零的红线：超卖、没有支付依据却确认收款、账本不平、虚构成交、越权读取客户数据。

## 第十七章　实施路线图：每一阶段怎样才算完成

本章原来的“退出条件”容易被理解成“退出平台”。本版统一改成：

> **阶段完成标准：当前阶段的关键能力已经被证明，才允许进入下一阶段。**

### 阶段 0：先把规则和责任说清楚

要完成：

- 确认运营主体、销售主体、合同、支付和发票责任；
- 发布产品、计价、验真、容量、退款和争议规则；
- 建立企业身份、权限和审计记录；
- 设计容量库存和订单预留。

**阶段完成标准：** 法务、财务、支付合作方和研发共同确认首笔交易方案，明确“谁收钱、谁交付、谁开票、出问题谁处理”。

### 阶段 1：跑通第一笔真实 GPU 交易

范围限定为：一家企业供应商、一家企业采购方、一个 GPU 产品、一个地区、一个固定时间窗。

**阶段完成标准：** 真实完成付款、容量锁定、交付、使用、验收、退款演练和对账，并且没有超卖和账本差异。

### 阶段 2：支持多家供应商

要完成：在线入驻、连接器配对、资源心跳、自动复验、容量部分取出、批量上架和并发预留。

**阶段完成标准：** 多家供应商能稳定上报；资源断联会停止新订单；已经成交的订单有明确的替换或应急交付流程。

### 阶段 3：加入模型小时和 Token 服务

要完成：模型版本、价格档位、输入/缓存/输出 Token 分项计量、模型实例小时和吞吐记录。

**阶段完成标准：** 同一模型的不同服务档位能区分；价格指数不会冒充某一模型的成交价；平台计量可以和供应商账单对上。

### 阶段 4：加入 NAS、机柜和跨区域服务

要完成：NAS 性能和数据删除验收、机柜和功率计价、长周期合同、跨区域资源发现和企业 API。

**阶段完成标准：** 长期和短期资源可以用同一套库存账规则记录，但验真、交付、迁移和取出条件分别写清楚。

### 阶段 5：受控扩大市场

只有真实交易、许可、税务、支付、反欺诈和争议机制稳定后，才评估更多地区、销售渠道、自动匹配或受控转让。扩大规模不能跳过资源核验、库存记录和交付证据。

## 第十八章　第一笔真实 GPU 交易验收清单

- [ ] 平台运营主体、规则和联系方式已明确；
- [ ] 供应商企业、资源归属、对公账户和开票信息已核验；
- [ ] 采购方企业和授权经办人已核验；
- [ ] GPU 规格、价格、时间窗、服务承诺和验收规则已固定；
- [ ] 资源已通过测试，且没有重复存入；
- [ ] 容量存入、预留、锁定、消耗和取出都有记录；
- [ ] 并发下单不会超卖；
- [ ] 支付回调能验签、核对金额并防止重复入账；
- [ ] 开通凭据能安全交付；
- [ ] 供应商和平台的计量差异在约定范围内；
- [ ] 客户完成验收或按合同自动验收；
- [ ] 退款能释放未使用容量，并冲回服务费和佣金；
- [ ] 资金、订单、容量和计量可以相互核对；
- [ ] 双方可以取得合同、订单、验真、计量和对账材料；
- [ ] 客服、事故、争议和数据删除的负责人已明确。

## 第十九章　治理红线

1. 不把算力描述成存款、股票、代币或保本收益产品；
2. 不让未核验的供应商直接公开销售；
3. 不允许同一容量重复挂牌或超卖；
4. 不以前端支付成功页面代替支付机构的正式通知；
5. 不用报价、补点或内部订单制造成交 K 线；
6. 不公开供应商底价、资源证明和商业机密；
7. 不允许供应商取出已经承担交付义务的容量；
8. 不收取代理入门费，不做多层级拉人返佣；
9. 未完成专项评估前，不开放资金钱包、提现、杠杆或自动做市；
10. 不以“快速上线”为理由跳过合同、验真、账本、支付验签、计量和审计。

## 第二十章　结语

算力市场真正缺少的不是更多价格页面，而是一套让买卖双方都能复核的共同规则。

KAI Cloud 的价值可以归纳为六件事：

1. 用标准产品说明买的是什么；
2. 用资源验真说明供应商是否真的能交付；
3. 用库存账说明容量有没有被重复销售；
4. 用价格方法说明参考价从哪里来；
5. 用订单、计量和验收说明服务是否完成；
6. 用支付、结算、退款和审计说明钱和责任如何闭环。

当供应商敢于提交真实容量，采购方能够比较并确认交付，平台能够解释价格和处理争议，算力才真正从分散资源变成可规模化采购的企业服务。

| GPU | 用于并行计算的处理器，常用于训练和推理 |

| API | 让客户通过程序调用服务的接口 |
| NAS | 通过网络提供文件或数据存储的设备或服务 |

| P25/P50/P75 | 一组可比价格的低位、典型值和高位分布指标 |
